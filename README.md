# 또박이 (Ddobaki)

어려운 행정·금융 문서를, 개인정보를 외부에 노출하지 않고 안전하게 이해할 수 있도록 도와주는 웹 앱입니다.

세금 고지서, 건강보험료 청구서, 연금 안내문처럼 복잡한 문서를 사진으로 찍으면, 중요한 부분만 형광펜으로 표시해 쉬운 말로 설명해줍니다. 특히 어려운 안내문을 접하기 쉬운 고령자나 사회초년생을 배려해 만들었습니다.

**배포 링크**: [ddobaki.vercel.app](https://ddobaki.vercel.app)

<br>

## 핵심 가치: "개인정보는 서버로 가지 않아요"

이 프로젝트의 가장 중요한 설계 원칙은 **개인정보를 원문 그대로 서버에 절대 전송하지 않는다**는 것입니다.

1. 사용자가 문서 사진을 찍으면, **브라우저 안에서** OCR로 텍스트를 인식합니다.
2. 이름처럼 자동으로 못 가리는 부분은 사용자가 직접 손가락으로 문질러 가립니다.
3. 주민등록번호, 전화번호, 카드번호, 계좌번호, 차량번호는 **정규식 기반으로 자동 마스킹**됩니다.
4. **가려진 텍스트만** 서버로 전송되어 AI 분석이 이루어집니다.
5. 확인이 끝나면 원본 이미지와 분석 결과는 **즉시 삭제**됩니다. (DB 없음 — sessionStorage/localStorage만 사용)

즉, 서버에는 어떤 개인정보도 남지 않는 구조로 설계했습니다.

<br>

## 실제로 발견하고 고친 보안 취약점

배포 후 실제 문서로 테스트하던 중, **은행 계좌번호가 마스킹되지 않고 그대로 전송되는 문제**를 발견했습니다.

기존 정규식은 "계좌" 또는 "계좌번호"라는 단어가 숫자 앞에 있어야만 마스킹하도록 되어 있었는데, 실제 세금 고지서의 "은행별 자동이체 계좌" 표는 이런 단어 없이 **은행명 + 숫자**로만 나열되어 있었고, 여기에 OCR 인식 노이즈까지 겹쳐 정규식이 패턴을 놓치는 경우가 있었습니다.

이를 계기로 마스킹 로직을 이중으로 보강했습니다.

1. **은행명 기반 매칭 강화** — 은행명 뒤에 오는 숫자를 폭넓게 인식하도록 정규식 확장
2. **길이 기반 안전망** — 위 패턴을 모두 놓치더라도, **숫자가 8자리 이상 이어지면 문맥과 무관하게 무조건 마스킹**하는 최종 방어선 추가

정규식은 "알려진 패턴만 잡아낸다"는 근본적 한계가 있다는 걸 실제 테스트로 확인했고, 이후로는 "패턴을 다 찾아낼 수 있다"는 전제가 아니라 "모르는 패턴도 있을 수 있다"는 전제로 방어선을 설계하는 방향으로 접근을 바꿨습니다. 날짜(예: 2026.8.31)나 금액(예: 129,390원)처럼 8자리 미만인 정보는 그대로 보존되어 AI 분석에는 영향이 없습니다.

<br>

## 왜 범용 AI 챗봇이 아니라 이 앱인가

문서 사진을 ChatGPT·Claude·Gemini 같은 범용 AI 챗봇에 그대로 올려도 비슷한 요약을 받을 수 있습니다. 이 프로젝트가 풀고자 한 문제는 "AI가 더 잘 요약하는가"가 아니라, **"그렇게 하면 안 되는 이유가 있다"**는 지점입니다.

| | 범용 AI 챗봇에 사진 업로드 | 또박이 |
|---|---|---|
| 원본 이미지 | 서버로 그대로 전송 | 브라우저 밖으로 나가지 않음 |
| 개인정보(이름·주민번호·계좌번호) | 원문 그대로 서버가 수신 | 마스킹된 텍스트만 전송 |
| 데이터 보관 여부 | 사용자가 통제하기 어려움 | 확인 즉시 삭제, 서버에 DB 없음 |
| 답변 신뢰 방식 | 텍스트를 그대로 신뢰해야 함 | 원문 근거 문장을 직접 대조 가능 |
| 사용 난이도 | 계정 생성, 프롬프트 작성 필요 | 사진 촬영 → 확인, 3단계 고정 플로우 |

세금 고지서나 보험료 청구서 같은 문서에는 이름·주민등록번호·계좌번호가 원본 그대로 담겨 있습니다. 이걸 범용 AI 서비스에 사진째로 올리는 순간, 그 데이터가 어떻게 저장·처리되는지는 사용자가 통제할 수 없습니다. 또박이의 차별점은 요약 품질이 아니라, **개인정보가 애초에 서버에 도달하지 않는 구조**를 만들었다는 데 있습니다.

## 핵심 파이프라인

```
사진 선택
  └─ 밝기 체크 (너무 어두우면 재촬영 유도)
       └─ 자르기 (선택 사항 — 필요한 구역만 크롭)
            └─ 가리기 (손가락으로 문질러 자유곡선 방식으로 마스킹)
                 └─ OCR 실행 (Tesseract.js, 확신도 낮으면 재촬영 유도)
                      └─ 정규식 기반 자동 마스킹 (주민번호·전화번호·카드번호·계좌번호·차량번호)
                           └─ 가려진 사진으로 최종 확인
                                └─ 마스킹된 텍스트만 서버로 전송
                                     └─ OpenAI로 문서 분석 → 구조화된 JSON 응답
                                          └─ 결과 화면 (요약 / 할 일 / 원문 근거)
                                               └─ 확인 완료 시 원본·분석 결과 즉시 삭제
```

## 기술 스택

### Frontend
- **Next.js 16** (App Router) — 라우팅 및 렌더링
- **TypeScript** — 정적 타입 검사
- **Tailwind CSS v4** — 유틸리티 기반 스타일링
- **Tesseract.js** — 브라우저 내 OCR (문서 텍스트 인식)
- **Canvas API** — 이미지 자르기, 형광펜 방식 개인정보 가리기 처리
- **Pretendard** — 한글 웹폰트

### Backend
- **Spring Boot 4.1** (Java 21) — REST API 서버
- **Maven** — 빌드 및 의존성 관리
- **Tomcat** — 내장 WAS (포트 8080)
- **OpenAI GPT 계열 모델** — 문서 내용 분석 및 요약 (구조화된 JSON 응답)

### 저장소 / 인프라
- **세션 스토리지 / 로컬 스토리지** — DB 없이 브라우저 저장소만 사용 (개인정보를 서버에 남기지 않기 위한 의도된 설계)
- **Railway** — 백엔드 배포
- **Vercel** — 프론트엔드 배포
- **GitHub** — 모노레포 (`jangabc3/ddobaki`)

### 왜 Spring Boot 4인가

2025년 11월 정식 출시된 Spring Boot 4를 선택했습니다. Spring Boot 3.5는 2026년 6월 30일부로 오픈소스 지원이 종료되어, 신규 프로젝트에서 최신 보안 패치를 받으려면 4.x가 사실상 유일한 선택지였습니다.

마이그레이션 과정에서 Jackson 2 → 3 전환(`ObjectMapper` → `JsonMapper`, 패키지 경로 변경), `spring-boot-starter-web` → `spring-boot-starter-webmvc` 네이밍 변경 등 실제 브레이킹 체인지를 직접 겪으며 대응했습니다.

## 트러블슈팅 & 배운 점

배포 후 실제 사용 과정에서 겪은 문제들을 **상황 → 원인 분석 → 해결 → 결과**로 정리했습니다. (가장 비중 있게 다룬 개인정보 마스킹 이슈는 위 "실제로 발견하고 고친 보안 취약점" 항목을 참고해주세요.)

### 1. 접근성 기능이 핵심 기능을 깨뜨린 좌표 버그

**상황** 고령자 사용자를 배려해 글자 크기를 확대하는 기능(`transform: scale`)을 넣었습니다. 그런데 "아주 큰 글씨" 상태에서 문서 자르기·가리기 화면을 써보니, 화면에 보이는 커서 위치와 실제로 그려지는 사각형/선의 위치가 서로 어긋났습니다.

**원인 분석** `zoom`은 브라우저가 레이아웃 좌표계 자체를 다시 계산해주지만, 크로스 브라우저(특히 Firefox) 호환을 위해 사용한 `transform: scale()`은 **화면에 보이는 크기만 확대할 뿐, 요소 내부적으로 좌표를 계산할 때 쓰는 크기(`getBoundingClientRect()`)는 그대로**라는 점을 확인했습니다. 즉 "보이는 크기"와 "코드가 계산에 쓰는 크기"가 확대 배율만큼 어긋나 있었습니다.

**해결** 마우스/터치 좌표를 절대값이 아니라 **컨테이너 안에서의 비율(0~1)로 먼저 환산**한 뒤, 그 비율을 스케일이 적용되지 않은 요소의 실제 크기(`offsetWidth`/`offsetHeight`)에 다시 곱하는 방식으로 바꿨습니다. 이렇게 하면 확대 배율과 무관하게 항상 정확한 위치가 나옵니다.

**결과 및 배운 점** 접근성을 높이려고 추가한 기능이 오히려 핵심 기능(정확한 마스킹 위치 지정)을 깨뜨릴 수 있다는 걸 확인했습니다. 새 기능을 추가할 때는 그 기능이 다른 기능의 "암묵적 전제"(여기서는 "화면 크기 = 계산에 쓰는 크기")를 깨뜨리지 않는지 점검해야 한다는 걸 배웠습니다.

<br>

### 2. 배포 후 계속 실패한 CORS/도메인 디버깅

**상황** Railway에 백엔드를 배포한 뒤, Root Directory를 `/backend`로 설정했음에도 배포 로그에 계속 Next.js(`next start`)가 찍히며 실패했습니다. 이후 Vercel 프론트엔드 배포와 CORS 설정까지 몇 단계에 걸쳐 비슷한 유형의 문제가 반복됐습니다.

**원인 분석** 문제를 단계별로 좁혀나갔습니다.
1. Root Directory 설정이 새 배포에 반영되지 않은 것으로 의심 → 수동 Redeploy로 확인
2. 배포 성공 후 API 호출 시 405 에러 → GET으로 직접 호출해 "서버는 살아있고 POST 전용 라우팅이 정상"임을 확인 (오히려 정상 신호)
3. 로컬(`localhost:3000`)에서 배포된 백엔드 호출 시 `TypeError` → CORS가 Vercel 도메인만 허용하고 있어 로컬 요청이 차단된 것으로 확인

**해결** 각 단계마다 "지금 실패가 배포 문제인지, 라우팅 문제인지, CORS 문제인지"를 구분하기 위해 브라우저에서 직접 엔드포인트를 호출해보거나 Railway 배포 로그를 확인하는 방식으로 원인을 좁혔습니다. 최종적으로 CORS 설정에 `localhost:3000`과 실제 배포 도메인을 모두 등록해 로컬 개발과 배포 환경을 동시에 지원하도록 했습니다.

**결과 및 배운 점** 배포 이슈는 증상만 보면 원인이 겹쳐 보이기 쉽다는 걸 경험했습니다. "405는 에러가 아니라 서버가 살아있다는 신호"처럼, 에러 코드 하나하나가 어떤 계층(빌드/라우팅/CORS/네트워크)의 문제인지 구분해서 접근하는 습관이 디버깅 속도를 크게 좌우한다는 걸 배웠습니다.

<br>

### 3. OCR 텍스트 대신 사진으로 최종 확인시키기로 한 결정

**상황** 처음에는 마스킹이 끝난 뒤 OCR로 인식한 텍스트를 사용자에게 보여주고 "이대로 전송해도 될까요?"라고 확인받는 방식으로 설계했습니다.

**원인 분석** 실제 문서로 테스트해보니, 표나 양식이 많은 문서에서는 OCR 인식률이 낮아 텍스트가 심하게 깨졌습니다. 사용자가 "이 텍스트가 내가 가린 부분을 정확히 반영하고 있는지" 판단할 방법이 사실상 없었고, 특히 고령자 사용자에게는 깨진 텍스트를 읽고 판단하라는 것 자체가 큰 부담이었습니다.

**해결** 확인 화면을 "OCR 텍스트 검토"에서 "가려진 사진 자체를 보여주고 확인"하는 방식으로 재설계했습니다. 사용자는 텍스트를 읽을 필요 없이, 자기가 방금 가린 사진을 눈으로 보고 놓친 부분이 없는지만 확인하면 됩니다.

**결과 및 배운 점** "기술적으로 가능한 검증 방법"과 "사용자가 실제로 할 수 있는 검증 방법"은 다르다는 걸 배웠습니다. 특히 이 앱의 핵심 사용자층(고령자·사회초년생)을 고려하면, 신뢰를 주는 방식은 정확한 데이터보다 "직관적으로 확인 가능한 형태"인 경우가 많았습니다.

<br>

### 4. 간헐적으로만 재현되는 AI 응답 실패

**상황** 배포 후 테스트 중 "지금은 AI가 답을 주지 못했어요"라는 에러가 가끔씩만 발생했습니다. 같은 문서로 다시 시도하면 대부분 성공했습니다.

**원인 분석** 매번 재현되지 않는 간헐적 문제라 처음엔 원인을 좁히기 어려웠습니다. "첫 번째는 실패하고 두 번째는 성공한다"는 패턴에 주목해, Railway 무료/하비 플랜 특성상 일정 시간 요청이 없으면 컨테이너가 잠들었다가 첫 요청에서 다시 깨어나는 데 시간이 걸리는 **콜드 스타트** 현상일 가능성이 높다고 판단했습니다.

**해결 및 배운 점** 완전히 없앨 수는 없는 인프라 특성이지만, 문제를 정확히 식별해두었다는 점에서 다음 단계(자동 재시도 로직 추가, 웜업 핑 등)로 대응 방향을 명확히 잡을 수 있었습니다. 간헐적으로만 재현되는 버그는 "재현 조건의 패턴"에 주목하는 것이 원인을 좁히는 핵심이라는 걸 배웠습니다.

<br>

### 그 외 짧게 겪은 이슈들

- **React 상태 업데이트 중첩 호출**: state setter 콜백 안에서 다른 state setter를 호출하면 이벤트가 이중으로 실행되는 문제가 있어, 외부 스코프의 값을 직접 참조하는 방식으로 해결했습니다.
- **OpenAI 응답 필드 누락/중복**: 초기에는 AI가 만든 `actionText`에 날짜가 중복으로 들어가거나 특정 필드가 비어 오는 문제가 있었습니다. 프롬프트에 예시(few-shot)를 명시하고, 필드별 책임을 명확히 분리(날짜는 `dueDate`에서만 표시)하는 방식으로 반복 개선했습니다.
- **Jackson 2 → 3 마이그레이션**: Spring Boot 4부터 `com.fasterxml.jackson.databind.ObjectMapper`가 아니라 `tools.jackson.databind.json.JsonMapper`를 써야 해서, 패키지 경로를 전면 교체했습니다.

## 기획 배경

부트캠프에서 Java/Spring Boot를 학습하며 예습 삼아 시작한 개인 프로젝트입니다. 세금 고지서나 건강보험료 청구서처럼 평소 접하기 어려운 문서를 받았을 때, 특히 고령자나 사회초년생이 이해에 어려움을 겪는 경우를 자주 접하면서 기획하게 되었습니다.

시중에 문서를 요약해주는 서비스는 많지만, 세금·보험료 고지서에는 이름·주민등록번호·계좌번호 같은 민감한 개인정보가 포함되어 있어 그대로 AI 서비스에 올리기 부담스럽다는 점에 주목했습니다. 그래서 "AI가 문서를 잘 요약해주는 것"보다 **"개인정보를 어떻게 안전하게 다룰 것인가"**를 이 프로젝트의 핵심 문제로 삼았습니다.

<br>

## 설계 과정에서 고민했던 지점들

**왜 서버에 원본을 아예 안 보내는 방식을 택했나**
개인정보를 암호화해서 저장하는 방식도 고려했지만, "저장하지 않으면 유출될 것도 없다"는 원칙이 더 확실하다고 판단했습니다. 그래서 DB 자체를 두지 않고, 마스킹까지 전부 브라우저에서 처리한 뒤 가려진 텍스트만 전송하는 구조로 설계했습니다.

**왜 OCR 텍스트가 아니라 사진으로 최종 확인을 시키나**
처음에는 OCR로 인식한 텍스트를 그대로 보여주고 확인받으려 했지만, 실제 문서로 테스트해보니 OCR 인식 품질이 낮아 텍스트만으로는 사용자가 "내가 가린 부분이 맞게 가려졌는지" 판단하기 어려웠습니다. 그래서 가려진 사진 자체를 보여주는 방식으로 확인 화면을 다시 설계했습니다.

**정규식 마스킹의 한계와 대응**
프로젝트에서 가장 중요하게 다룬 문제입니다. 자세한 내용은 위 "실제로 발견하고 고친 보안 취약점" 항목을 참고해주세요.
